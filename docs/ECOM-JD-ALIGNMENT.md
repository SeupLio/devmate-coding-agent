# 与「AI 产品实习生-【电商】」JD 的对齐说明

> 目标岗位：快手电商 · 服务商工作台 · AI 产品实习生（杭州）
>
> 这份文档逐条对照 JD，说明项目里有什么、缺什么。
> 缺口不回避 —— 面试被追问到才发现没准备，比写在简历上被拆穿要好。

---

## 0. 先说清楚：这个项目原来是什么，我做了什么

原项目 **DevMate** 是一个**编码 Agent**（对标 Claude Code）。这份 JD 要的是
**电商业务场景的 AI 产品**，两者看似不搭。

我的做法不是硬套，而是：**把 DevMate 里可复用的能力抽出来，落到电商服务商的真实业务场景**。

| 原项目里已有的能力 | 迁移到电商场景后 |
|---|---|
| 知识库检索（RAG，Markdown 切块 + TF-IDF） | → 电商业务知识库（平台规则 / SOP / 方法论 / 案例） |
| 工具编排 + 结构化输出 | → 打标引擎、诊断引擎（结构化规则 + 可解释输出） |
| 评测体系（含变异测试、外部基准） | → Prompt 变体效果对比（可统计的 Prompt 迭代） |
| trace / 成本可观测 | → 沿用（每次 AI 调用的耗时与成本可量化） |

**这本身就是产品思维的体现**：不是「我有个锤子所以到处找钉子」，而是
「识别出哪些能力是可迁移的、哪些场景值得做」。

## 一、工作职责逐条对照

### 1. 围绕商家服务、线索跟进、**经营诊断**、**任务推荐**、**话术生成**，梳理 AI 可落地的业务机会

| 场景 | 项目里的实现 | 状态 |
|---|---|---|
| 商家服务 / 线索跟进 | 商家列表按**跟进优先级 P0/P1/P2** 排序（规则见 `tagging.ts`） | ✅ |
| **经营诊断** | `diagnosis.ts`：4 项核心指标按达标线判定 → 健康分 + 问题清单 + 可执行动作 | ✅ |
| **任务推荐** | 诊断产出**按「影响/难度」排序**的推荐任务（最多 3 条，附负责人与预期） | ✅ |
| **话术生成** | `script.ts`：基于打标 + 诊断 + 知识库检索生成跟进话术，生成后自动质检 | ✅ |

**产品判断（面试可直接讲）**：任务推荐为什么要按「影响 ÷ 难度」排序，而不是按严重程度？
因为方法论里写明「先看影响最大且**最好改**的」—— 客服响应慢（难度 1）比退款率高（难度 4）
更该先做。把最严重但最难改的排在最前面，商家做不完就失去信任。
**这条规则写在代码里、可被运营调整**，而不是藏在提示词里。

### 2. 业务数据、商家案例、跟进记录等内容的**清洗、整理、分类和打标**

实现：`taxonomy.ts`（标签体系）+ `tagging.ts`（打标引擎）。

- **7 个标签维度**：线索阶段 / 商家类目 / 经营健康度 / 商家规模 / 跟进优先级 / 商家痛点 / 话术意图
- 每个取值都带**判定口径（criteria）**—— 这是「让不同人打出同样标签」的前提
- **可解释**：每个标签带 `evidence`（为什么打这个标），运营能复核、能纠错
- **带置信度**：数值硬判定 = 1.0；关键词命中 = 0.6~0.9；**多信号交叉有加成**
- **低置信度自动标记「需复核」**（< 0.7），前端标黄提示
- 批量打标输出**覆盖率 + 需复核比例** —— 这就是「沉淀高质量基础数据」的度量

**产品判断**：为什么打标用规则而不是全交给 LLM？
打标是**基础设施**不是创作：规则可解释、可复现、零成本零幻觉。
让 LLM 去判断「退款率 15% 算不算高」，既浪费又可能出错。LLM 的位置是**兜底**
（自由文本里的口语化表达），不是主判定。

### 3. 协助搭建和维护**业务知识库**（平台规则、经营方法论、服务商 SOP、常见问题、优秀案例）

实现：`assets/ecom-knowledge/` 四篇结构化文档 + 复用 `knowledge.ts` 的 RAG 检索。

| JD 要求 | 已建文档 |
|---|---|
| 平台规则 | `01-平台规则.md`（保证金 / 违规处罚 / 仅退款 / 活动门槛 / 结算） |
| 服务商 SOP | `02-服务商SOP.md`（五阶段标准动作 + **跟进记录规范** + 禁止事项） |
| 经营方法论 | `03-经营方法论.md`（核心漏斗 / 达标线 / 诊断优先级 / 分规模策略） |
| 优秀案例 | `04-优秀案例.md`（3 个脱敏案例 + 可复用点 + 引用规范） |
| 常见问题 | 并入 01/02（仅退款、活动报名、结算等高频问题） |

**实测检索效果**（4 组真实业务问题，全部命中正确小节）：

| 查询 | 命中 |
|---|---|
| 仅退款规则 | 01-平台规则 / 仅退款规则 |
| 转化率低怎么诊断 | 04-优秀案例 / 案例一（女装转化率） |
| 客服响应慢 | 03-经营方法论 / 关键指标与达标线 |
| 新店没流量怎么办 | 04-优秀案例 / 案例三（长尾新店） |

**产品判断**：知识库文档里**写进了「跟进记录规范」**（记事实不记情绪、用明确痛点词汇）。
因为下游的自动打标质量**取决于上游记录质量** —— 这是「数据链路」视角，
而不是把知识库当成一个孤立的文档仓库。

### 4. 参与 AI 工具、智能助手、**Prompt、工作流**等方案的**测试和优化**，记录效果问题并协助迭代

实现：`script.ts` 的 **Prompt 变体对比器**（`compareVariants`）+ 话术自动质检。

- **3 个 Prompt 变体**，每个都写明**设计取向**：
  - V1 直给式（基线，验证「加约束到底有没有用」）
  - V2 结构约束式（强制三段：具体观察 → 价值建议 → 明确下一步）
  - V3 角色扮演 + **反例式**（明确写出「差的话术长这样」）
- **同一套指标打分**：平均质量分 / 违规率 / 生成成功率
- **输出「下一步该改哪里」**：统计该变体最常不通过哪一项
- 质检 5 项：SOP 禁止事项 / 含具体数据 / 无空话套话 / 有下一步 / 长度适中

**质检器已用手写样本验证**（确定性部分）：

```
好话术    → 质量分 1.00   违规 false
差话术    → 质量分 0.00   违规 true（检出「承诺无法保证的结果」+ 空话套话 + 缺数据 + 缺下一步）
违规话术  → 质量分 0.20   违规 true（检出「索要账号密码」）
```

⚠️ **诚实说明**：端到端的「多变体真实对比」**本次未能跑完** ——
LLM API 配额在跑之前用尽（`HTTP 429: ApiKey已触发限额`）。
代码与质检器已验证，但**没有真实的变体对比数据**。
这条在面试时应如实说「设计已完成、确定性部分已验证、端到端待额度恢复后补跑」，
而不是编一组数字。

### 5. 竞品调研、业务访谈、需求整理、**原型设计**、数据分析

| 要求 | 项目里的对应 |

## 二、任职要求逐条对照

| 要求 | 项目证据 |
|---|---|
| 本科及以上在读，产品/计算机/电子商务等相关专业 | ——（个人背景） |
| 对 AI 产品、大模型应用、智能助手、Agent、知识库等方向有兴趣 | 完整实现了一个 Agent 产品 + 知识库 RAG，并有外部基准实测 |
| **逻辑清晰、细心耐心**，能完成大量信息整理、数据清洗、标签归类和文档沉淀 | 7 维标签体系（每维带判定口径）+ 打标置信度与复核机制 + 4 篇结构化知识库 + 完整交接文档 |
| **具备基础的产品思维**，能将零散信息整理成结构化内容 | 见下 |
| 熟练使用文档类工具；会使用 AI 工具提升效率者优先 | 全部文档为 Markdown 结构化产出；用 Agent 辅助开发 |

**关于「产品思维」**，项目里有几个刻意的产品决策，面试时可以直接讲：

1. **任务推荐按「影响 ÷ 难度」排序**，而不是按严重程度 ——
   因为商家做不完就失去信任，先给最好改的。
2. **数据不足时不给结论**：只拿到 1 个指标的商家，诊断输出「数据不足，请补充 X」，
   而不是硬凑一个结论。**这关系到服务商在商家面前的可信度**。
3. **打标低置信度标黄提示复核**，而不是假装所有标签都可靠。
4. **话术必须「有据可依」**：输入是打标 + 诊断 + 知识库检索，
   模型是在「把已有结论讲成人话」，不是凭空创作 —— 这样话术不会退化成通用套话。
5. **打标用规则而非 LLM**：能确定性判断的事不该问模型（成本、可解释性、可复现性）。

## 三、诚实缺口清单

| 缺口 | 说明 | 影响 |
|---|---|---|
| **Prompt 变体对比未跑完** | LLM 配额耗尽（429），只有确定性质检器的验证 | 面试时如实说明，额度恢复后可补 |
| **数据是合成的** | `demo-data.ts` 里 6 个商家是编的，不是真实业务数据 | 字段结构真实，可无缝替换为数仓数据 |
| **未接真实业务系统** | 没有对接快手电商的商家数据、CRM、跟进记录 | 本环境无此权限 |
| **无竞品调研 / 业务访谈** | JD 第 5 条的一部分 | 需要真实调研渠道 |
| **无真实商家反馈** | 话术质量分只反映「结构合规性」，不反映「商家真实回复率」 | 需要真实投放数据 |

## 四、如果继续做，优先级建议

| 优先级 | 事项 | 为什么 |
|---|---|---|
| **P0** | 补跑 Prompt 变体对比（额度恢复后） | 这是 JD 第 4 条最直接的证据 |
| **P0** | 用真实商家数据替换 demo 数据 | 「数据清洗打标」的可信度取决于数据真实性 |
| **P1** | 打标接入 LLM 兜底（自由文本抽取） | 规则覆盖不到的口语化表达 |
| **P1** | 话术效果回流（记录商家回复率，反哺 Prompt 迭代） | 从「结构合规」升级到「真实效果」 |
| **P2** | 竞品调研与业务访谈 | JD 第 5 条，需要线下资源 |

## 五、一句话总结

> 这份 JD 的五条职责里，**四条有真实实现**（场景落地、数据打标、知识库、Prompt 测试），
> **一条部分实现**（原型设计有、竞品调研/业务访谈无）。
>
> 三个明确的诚实缺口：**Prompt 对比未跑完（额度）**、**数据为合成**、**未接真实业务系统**。
>
> 最值得在面试里讲的不是「我做了多少功能」，而是
> **「我知道哪些该用规则、哪些该用模型，以及为什么」** —— 这是产品岗比技术岗更看重的东西。
