# 电商打标/诊断：评测方法论

> 复现命令：`bun run ecom:eval`（报告落盘 `benchmarks/ecom-eval/report.md`）

---

## 一、为什么这个模块必须有评测

模块原有 2000+ 行代码，**没有任何 ground truth**。这意味着一个致命问题：

> 「打标准不准？」—— **无法回答**。

能演示「它能跑」，但说不出「它有多准」。没有准确率就没有迭代方向，
也无法向业务方证明价值。所以补了评测体系 —— 这是这一轮最核心的改动。

---

## 二、两个集合，两种问法（关键设计）

| | 回归集 `GOLDEN_SET` | 挑战集 `CHALLENGE_SET` |
|---|---|---|
| **样本数** | 24 条 | 10 条 |
| **怎么标的** | 按 `taxonomy` 口径人工标注 | 同样按口径标，但输入是**真实口语变体** |
| **预期结果** | **必须全对** | **预期会失败** |
| **作用** | 锁定口径，防回归 | 测泛化，暴露真实弱点 |
| **实测** | 宏 F1 **100%** | 单标签 **100%**、痛点 **60%** |

### 为什么「回归集 100%」不能当作成绩

金标准与规则**同源**（都来自同一份 `taxonomy` 口径），所以回归集 100% 是
**循环论证**，它证明的只是「口径没被改坏」，不是「规则很准」。

**真正诚实的数字来自挑战集** —— 那里用运营真实会说的话去为难规则：

| 样本 | 输入 | 期望 | 挑战什么 |
|---|---|---|---|
| C01 | 「优选**衣服**店」 | apparel | 类目同义词（词表只有「服装/服饰」） |
| C02 | 「**转化不行**，一直没起色」 | low_conversion | 痛点口语同义 |
| C05 | 「回复**要等很久**」 | slow_response | 痛点口语同义 |
| C06 | 「客服**没人理**」 | slow_response | 痛点口语同义 |
| C08 | 「**已加微信**」 | contacted | 阶段口语同义 |
| C07 | 四项指标全在预警区 | at_risk | **口径缺陷**（旧口径判「健康」） |
| C03 | 「**已经没有**仅退款问题了」 | 不打标 | **能力边界**：否定句 |
| C04 | 「**之前**退款多，**现在已经降下来**了」 | 不打标 | **能力边界**：时态 |
| C09 | 「客服响应要 **120 秒**」 | slow_response | **能力边界**：文本内数字 |
| C10 | 「宠物用品店」 | other | **对照组**：不在体系内应正确归「其他」 |

## 三、评测驱动的两轮真实改进

### 第一轮：词表覆盖（该修的）

挑战集首跑：**单标签宏 F1 78.9%，痛点 F1 0%**。8 处失败中 5 处是词表覆盖不足。

修复：补同义词（`衣服`、`转化不行`、`回复要等很久`、`没人理`、`已加微信`）。
→ 单标签回到 100%，痛点从 0% 升到 60%。

### 第二轮：口径缺陷（更值钱的发现）

C07 暴露了一个**真实口径漏洞**：四项指标**全部**处于预警区（0 项严重）的商家，
旧口径判为「健康」—— 但「全项平庸」显然比「一项严重、三项优秀」更该被关注。

**修复过程中踩了一个坑，值得记录**：

第一次修法用「预警项 ≥ 3 就判亚健康」，结果**回归集里 2 个正常样本被误判**
（G04、G13）—— 因为**达标线是「优秀线」而非「正常线」**，
多数商家天然低于它，一低于就判亚健康会让标签失去区分度。

最终改成「**已测指标全部**低于达标线才判亚健康」，既不误伤正常商家，又抓住了全项平庸。

**同一个修复还牵出优先级的问题**：C07 变亚健康后，优先级被抬到 P0。
但 P0（立即跟进）是**稀缺资源**，不该被「平庸」占用 —— 真正有严重问题的商家会被挤到后面。
于是把优先级的「有风险」从「health 标签是 at_risk」改为「**存在严重项**」。

> 这两处修改都不是我一开始设计出来的，是**被评测数据逼出来的**。
> 这就是有 ground truth 和没有 ground truth 的区别。

## 四、指标口径（避免被误读）

| 指标 | 回答 | 误读风险 |
|---|---|---|
| Precision | 打出的标有多少是对的 | 高 Precision 低 Recall = 保守，会**漏标** |
| Recall | 该打的标打了多少 | 高 Recall 低 Precision = 激进，运营要**花时间纠正** |
| **Kappa** | 口径能否交接 | 准确率高但 Kappa 低 = 靠类别不平衡刷分 |
| **P@K / NDCG@K** | 优先名单前几名准不准 | 只报分类准确率会掩盖排序问题 |
| 数据质量四维 | 上游数据能不能用 | 打标的上限由它决定 |

**Kappa 判读（Landis & Koch）**：<0.2 差 ｜ 0.2~0.4 一般 ｜ 0.4~0.6 中等 ｜ 0.6~0.8 好 ｜ >0.8 极好

## 五、阈值校准：一个「没有收益」的诚实结论

实现了网格搜索校准（`calibrate()`），搜索 **2304 种阈值组合**，目标函数是
阈值敏感的三个维度（scale / health / priority）的宏平均 F1。

**结果：提升 0.0%，未达显著。**

这不是失败，是**正确的结论**：

- 默认口径已接近该样本上的最优；
- 更重要的：**样本只有 24 条，而待调参数有 6 个** ——
  在这个规模上做网格搜索**必然过拟合**，很可能只是把阈值调到恰好匹配这 24 条，
  换一批数据反而更差。

所以 `calibrate()` 内置了显著性判断：提升 < 0.05 时明确输出
「**不建议据此修改线上阈值**」。

> 一个「调参没有收益」的结论，比一个「调参提升 3%」的数字更有价值 ——
> 后者很可能是过拟合，前者避免了把噪声当信号上线。

## 六、回归锁定

评测体系已接入单测（`tests/agent.test.ts`）：

- **回归集必须全对** → 任何不一致说明改动破坏了已定口径
- **挑战集只允许 3 处已知边界失败**（C03/C04/C09）→ 数量变多即泛化能力退化
- **口径单一来源**：打标与诊断对同一商家必须给出同源结论
- **阈值可配置**：换类目预设会改变判定结果（证明阈值不是写死的）
- **校准诚实性**：样本量不足时必须报告「未达显著」

`bun run ecom:eval` 在挑战集出现「非已知边界」失败时以非 0 退出，可直接用作 CI 门禁。
