# 这个项目放在 Agent 开发岗简历上，够不够？

> 这份文档回答四个问题：
> 1. 「浏览器端 Agent 页面 + 离线自测指标」够不够？
> 2. 项目的**特色**到底在哪？
> 3. 会不会过于基础？
> 4. 下一步该补什么（按**简历增益**排序，不是按生产就绪排序）
>
> 结论先行：**项目本身不算基础，但「定位」和「叙事」把它讲小了。**
> 它现在是一个「中级偏上」的 Agent 工程作品，
> 最大的问题不是功能少，而是**没有一个能被一句话说清的「最难的技术点」**。

## 1. 「页面 + 离线评估」够吗？

**不够，而且这个描述本身就是问题。**

因为这两件事都是**门槛级**的：

| 被当成卖点的事 | 真实稀缺度 |
|---|---|
| 用 Next.js 搭一个聊天页面 + SSE | 低 —— 教程级别的量 |
| 接 OpenAI 兼容接口、搞个工具调用循环 | 低 —— 一周能复刻 |
| 内置十几个工具 | 中 —— 拼的是设计品味，不是难度 |
| 写几个测试、跑个通过率 | 低 —— 「离线自测指标」如果题目是自己造的，等于自证 |

**所以你的直觉是对的**：如果简历上写的是「做了一个浏览器端 Agent 页面，并做了离线评测」，
面试官的反应会是「哦，又一个套壳聊天机器人」。

**但项目实际上远不止这些** —— 问题出在**没把真正难的东西讲出来**。

## 2. 真正的特色在哪（已经在项目里，只是没被讲）

按「别的候选人做不出来的程度」排序：

### ⭐⭐⭐ 特色一：能从真实 GitHub 提交**自动生成**可验证任务的评测流水线

大多数人的「评测」是：自己写几个题目 → 自己写断言 → 自己判分。
**这等于自证。** 本项目的做法是（`src/lib/bench/builder.ts`）：

```
真实修复提交 fix
  ├─ base = fix 的父提交 → 拉真实仓库快照
  ├─ 把 fix 里的测试文件覆盖到 base（Agent 看不到）
  ├─ 阶段1 跑测试 → 失败集合 = FAIL_TO_PASS 候选
  └─ 阶段2 套用 fix 的源码 → 必须全通过
        └─ 两段都成立才收录
```

**判据是机器跑出来的，不是我写的。** 我无法让实现去迁就断言，
因为断言来自上游仓库；也不会出现「本来就能过」的伪任务。

> 这一条单独拎出来就够讲 10 分钟，因为它证明的是**方法论能力**，
> 而不是「会用某个库」。

### ⭐⭐⭐ 特色二：诚实到反直觉的负结果

> 玩具任务 **100%** → 真实任务 **0%**。

同一个 Agent、同一个模型，只换任务来源，成绩从满分掉到零。
而且不止报数字，还**定位到了具体轨迹**：

- Agent 把 30 步预算全花在反复读同一段代码（`lib/parser.js` 被读了 8 遍），
  最后一次改动出现在第 26 步，收尾时还在「准备动手」
- 修复后 `no_edit` 从 4 → 1，但**通过率没有提升** ——
  失败从「压根没动手」变成「动手了但没做对」

**能主动讲自己的负结果、并且把它拆解成可修复的机制问题**，
这是资深工程师和「刷分选手」最明显的分水岭。

### ⭐⭐ 特色三：攻击自己的评测器（变异测试自检）

`src/lib/eval/sensitivity.ts` 会**故意制造 11 个「作弊实现」**
（删测试、写死断言、不跑测试直接返回成功……），
验证评测器能否全部识破。

**绝大多数项目的评测器从来没被验证过**，而这个项目会证明「我的评测器不会误报通过」。

### ⭐⭐ 特色四：延迟的工程化处理

- 规划是一次**静默的完整 LLM 往返** → 改成按需规划（短任务跳过）
- 推理模型的思考内容原本**根本没被解析** → 解析 `reasoning_content` 并流式展示
- 加「深度思考 / 快速模式」开关（实测关思考总耗时快约 3×，但首屏更慢）

这些不是「加功能」，是**对着真实延迟数据做的工程权衡**。

### ⭐ 特色五（本次新增）：工具无关的运行时

内置工具再多也是「我写死的」。本次接入 **MCP**：
Agent 启动时连外部 MCP 服务器，**运行时**发现工具并调用。

实测（`bun scripts/mcp-smoke.ts`）：

```
✓ 运行时发现 3 个 MCP 工具：
    mcp__demo__get_time    (readOnly=false)
    mcp__demo__word_count  (readOnly=false)
    mcp__demo__sha256      (readOnly=false)
  · 调用 MCP 工具 mcp__demo__get_time
MCP 工具返回：2026/10/5 17:02:43（Asia/Shanghai）
✓ 冒烟通过：Agent 在运行时发现并成功调用了外部 MCP 工具
```

并且**并行工具调度**按副作用分级：只读工具并发、写工具串行
（`edit_file` / `git_operation` 并发会互相踩）。

## 3. 还欠缺什么（按**简历增益**排序）

我把欠缺分成两类 —— 这个区分很重要：

### A 类：工程卫生（不做会被问，做了不加分）

Docker 沙箱、CI 门禁、限流、密钥管理、E2E 测试。
这些**面试官会问「你考虑过吗」**，但做完了也只是「合格」。

### B 类：决定你能不能拿到 offer 的（按增益排序）

| 缺口 | 为什么是增益 | 大概工作量 |
|---|---|---|
| ~~1. 可观测性（trace + 成本账本）~~ | ✅ **已完成** | — |
| ~~2. 权限模型 + 人在环~~ | ✅ **已完成** | — |
| **3. 真实部署 + 公开链接** | **最大的缺口**：没有人用过 = 没有被验证过。哪怕只是公网 demo + 10 个真实用户 | 小 |
| **4. 子 Agent 委派** | 「上下文隔离的委派」是现代 Agent 架构的标志（Claude Code 的 Task 工具） | 中 |
| **5. 多模型矩阵 + 成本对比** | 证明你会做 tradeoff，而不只是「跑通」；现在有了成本账本，做这个的边际成本很低 | 小 |
| **6. 摘要式上下文压缩** | 现在的占位符截断会**永久丢信息**，Agent 后面还得重读一遍 | 中 |
| **7. Prompt cache 友好的上下文布局** | 实测 cache 命中率已有 90%，继续优化空间明确 | 小 |

**如果只做一件事**：做 **4（部署）** —— 因为它把「我写了个项目」变成「有个东西在跑，有人用过」。
**如果做两件**：加 **1（可观测性）**，因为它是所有后续优化的前提。

## 4. 三条可以讲的主线故事（挑一条讲透，别全讲）

简历上项目的正确写法不是罗列功能，而是**一句话说清最难的技术点 + 一个可验证的结果**。

**故事 A（方法论向，最推荐）**
> 我建了一套能从真实 GitHub 修复提交自动生成可验证任务的评测流水线（机器推导 FAIL_TO_PASS，
> 而非手写断言），并用它证明我的 Coding Agent 在真实仓库上通过率只有 0–17%
> —— 而同一套 Agent 在自造任务上是 100%。我据此定位到「步数全花在重复读取上」的机制问题并修复，
> `no_edit` 失败从 4/6 降到 1/6。

**故事 B（架构向）**
> 我把 Agent 的工具层做成了**运行时动态发现**（MCP）+ **按副作用分级并发调度**：
> 只读工具并发、写工具串行。这让 Agent 能接入任意外部工具服务器，
> 而不是依赖我硬编码的工具集。

**故事 C（生产向）**
> 我给 Agent 加了完整的可观测性与权限模型：每次运行产出可回放 trace 与成本账本，
> 危险操作需要人工审批，敏感文件读取被拦截。
> （⚠️ 这条**现在还不能讲**，因为还没做）

## 6. 一句话总结

> **不是项目太基础，是它没被讲成它本来的样子。**
>
> 一个「聊天页面 + 离线自测」确实是教程级；
> 但「一套能从真实提交自动生成可验证任务的评测流水线，
> 用它把自己的 Agent 从 100% 打到 0%，定位到机制问题并修复，
> 再把工具层做成运行时动态发现 + 分级并发」——
> 这是**方法论 + 架构 + 诚实**三样都占的作品。
>
> 缺的最后一块拼图是：**让别人也能用上它**。
