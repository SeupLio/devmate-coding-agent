# 简历表述：DevMate（Agent 主体 + 电商扩展）

> **当前版本，替代 `RESUME-ECOM.md`。**
>
> 写法原则：
> 1. **给 HR 看**，不是给同行看 —— 少术语，先讲清「解决了什么问题」
> 2. **Agent 为主体**，电商扩展是一句延伸（体现能力可迁移）
> 3. **成果只用外部权威证据** —— 题目与判分标准由第三方定义的基准；
>    自建标注集上的指标（如 Kappa 1.00、宏 F1 100%）**不作为成果**，只作为过程佐证
> 4. 字数与原简历格式对齐（日期 / 项目名 / 独立完成 / 三段）

## 一、通用版（约 330 字，投 AI / 研发 / 产品岗）

> **2026.09　《DevMate — AI 编码助手（Coding Agent）》　独立完成**
>
> **项目描述**：AI 编码助手普遍存在「过程看不见、结果不敢信」的问题。独立从 0 到 1 完成一款 AI 编码助手产品：让 AI 自主读代码、改代码、跑测试，同时做到全过程可视、危险操作可拦截、结果由测试客观验收。
>
> **负责工作**：独立完成全部设计与开发（后端 5300 行、前端 2100 行）。搭建 AI 自主执行任务的完整闭环——任务规划、工具调用、执行验证、流式交付；实现 18 个代码工具，并支持按标准协议接入外部工具；在「效率」与「安全」之间做产品权衡，设计分级权限与人工审批机制，常规操作免确认、危险操作强制拦截；建立全过程追踪与成本账本，使每次任务可量化、可归因。
>
> **成果**：①在两项国际公开基准上完成验证（题目与判分标准均由第三方定义，非自造用例）：伯克利函数调用榜 BFCL 200 题准确率 **75.0%**，Aider 编码基准 49 题解决率 **93.9%**；②为检验评测体系本身是否过松，主动注入 **11 个缺陷变异体**做敏感度验证，全部被检出；③沉淀产品需求文档与评测方法论，含指标口径、验收标准与三阶段迭代规划。

## 三、为什么这样改（对照上一版）

| 上一版问题 | 这一版怎么改 |
|---|---|
| 以电商场景为主，**Agent 主体的 5300 行工作没体现** | Agent 为主体，电商只作成果③的一句延伸 |
| 把自建标注集的 Kappa 1.00 / 宏 F1 100% 当成果 | **移出成果** —— 自建集上的数字不能证明能力，只在过程描述里提「可量化」 |
| 「泛化能力 78.9%→100%」是自测集内部对比 | 删掉。外部基准（BFCL / polyglot）才是可信证据 |
| 术语堆砌（plan→act→observe、NDCG@K、MCP、TF-IDF） | 换成 HR 能懂的话：「任务规划、工具调用、执行验证」 |
| 没说清项目背景为什么值得做 | 开头一句点出行业痛点「过程看不见、结果不敢信」 |
| 工作量模糊 | 给出可核对的规模（后端 5300 行 / 前端 2100 行 / 18 个工具） |

## 五、面试要主动说的两个诚实缺口

不写进简历，但被问「还有什么不足」时要**主动**说 —— 主动承认比被挖出来强。

1. **真实任务解决率远低于基准**：用 SWE-bench 方法论从真实修复提交推导的可验证任务上，
   解决率只有 **0~17%**，而自建玩具任务是 100%。这个差距说明**基准分数不等于真实工程能力**。
   （正是这个发现促使我去接外部基准，而不是继续用自建集自证。）
2. **电商模块没有真实业务数据**：所有商家数据是合成的，
   因此**业务指标（回复率、有效跟进率）一个数字都没有** —— 只做到了「能力可量化」，
   没做到「业务效果可验证」。
