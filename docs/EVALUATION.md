# DevMate 评测方法论

> 这份文档回答一个问题：**「评测集 4/4 通过」这句话到底能说明什么？**
>
> 单看通过率，什么都说明不了——它既可能是「系统很强」，也可能是「题目太简单」或「评测太松」。
> 下面四层设计，分别用来堵住这三个漏洞。

---

## 0. 评测体系总览

| 层 | 手段 | 回答什么问题 | 需要 LLM |
|---|---|---|---|
| L1 | **单元测试**（67 条） | 代码有没有坏？沙箱安全、工具、检索、压缩、失败分类是否正确？ | 否 |
| L2 | **任务评测集**（4 常规 + 4 held-out + 3 难任务） | 端到端链路能不能跑通？跨文件任务能不能做？ | 是 |
| L3 | **对照实验**（ablation，7 组 + 裸模型） | 每个能力维度各自贡献多少？ | 是 |
| L4 | **评测灵敏度检查**（mutation testing，11 变异体） | 评测本身是不是太松？ | **否** |
| L5 | **失败模式分类** | 没通过的任务，**为什么**没通过？ | 否（消费 L2 的 trace） |

关键点：**L4 / L5 不需要 LLM，秒级完成**，却是最能反驳「评测太松」和「通过率说明一切」的两层。

## 1. L2 · held-out 任务集（SWE-bench 方法论的小规模复刻）

### 1.1 为什么需要 held-out

常规 4 个任务（`fix-bug` / `add-feature` / `perf-refactor` / `write-doc`）是我在开发过程中
反复调试用的，我对它们的难度有先验、断言也随着实现调整过——这是**过拟合风险**。

held-out 集的做法（对齐 SWE-bench）：

| 维度 | 常规集 | held-out 集 |
|---|---|---|
| 项目 | `mathutils`（数学工具库） | `stringutils`（字符串工具库，**另一个域**） |
| 断言来源 | 部分为「按实现写的正则」 | **100% 来自预先写好的测试文件** |
| 是否参与调试 | 是 | **否**（只在正式评测时跑） |
| 任务数 | 4 | 4 |

### 1.2 FAIL_TO_PASS 设计

`assets/holdout-project/` 里，`stringutils.test.js` **预先写好且当前失败**：

```
初始状态：node --test  →  3 pass / 9 fail
  分组 slugify    → exit 1（实现有 bug）
  分组 camelCase  → exit 1（大小写处理错误）
  分组 truncate   → exit 1（函数未实现）
  分组 initials   → exit 1（函数未实现）

参考解（人工编写）：node --test  →  12 pass / 0 fail
```

断言直接取 `node --test --test-name-pattern=<分组>` 的**退出码**，
不含任何针对实现细节的正则 —— 因此 Agent **无法通过「迁就断言」来刷分**。

### 1.3 防作弊断言

L2 原本有一个真实盲区：只断言 `node --test` 退出码，那么 **Agent 只要删掉测试或清空 assert
就能让退出码变成 0**，「测试通过」于是变成一句空话。

修复：增加断言「原有测试用例未被删减」——
要求模板里的测试名一个不少，且 `assert.` 调用数不少于模板。
这样既允许 Agent **新增**用例（`add-feature` 任务需要），又禁止**删减**原有用例。

> 这个盲区是 L4（灵敏度检查）发现的，不是想出来的。

## 1.5 L2-hard · 难任务集（多文件 / 长链路 / 环境反馈）

常规集与 held-out 集都是**单文件、单 bug**，强模型 single-shot 就能做对（见 §5），
区分度不足。难任务集 `assets/hard-project/` 针对这个短板设计：

```
hard-project/
  src/lexer.js       词法分析（初始不支持 = 与 ;）
  src/parser.js      语法分析（初始优先级错误、无一元负号、无多语句）
  src/evaluator.js   求值（初始 % 为 JS 余数、无赋值）
  src/index.js       API：evaluate(expr, env?)
  test/calc.test.js  预置测试（FAIL_TO_PASS），分 precedence / variables / golden 三组
  tools/reference.js 参考实现（环境反馈 oracle）
  tools/trace.js     诊断脚本（打印 token 流与 AST）
  data/cases.json    表达式用例（期望值不在文件里）
```

三个任务分别命中一种「难」：

| 任务 | 难点类型 | 为什么难 |
|---|---|---|
| `hard-precedence` | **多文件追踪** | 优先级缺陷在 parser，但要读懂 lexer 的 token 形态与 evaluator 的求值路径才能定位；还要补一元负号 |
| `hard-variables` | **长链路改造** | 一个特性贯穿 lexer（新 token）→ parser（语句/赋值）→ evaluator（变量环境）三个文件 |
| `hard-golden` | **依赖环境反馈** | 期望值**不在任何文件里**：测试只比对 `data/expected.json`，而该文件需要运行 `node tools/reference.js --emit` 才能生成 |

### 1.5.1 为什么 `hard-golden` 是「必须依赖环境反馈」

测试断言是 `evaluate(expr) === expected[expr]`，而 `expected` 来自 `data/expected.json`，
该文件初始**不存在**。Agent 无法通过读代码或读测试得到期望值，只能：

1. 运行 `node tools/reference.js --emit`（环境反馈）拿到真值；
2. 写入 `data/expected.json`；
3. 运行测试，发现 `%` 语义不符（JS 余数 vs 数学取模）；
4. 修改 `src/evaluator.js`。

这条链路把「run → observe → fix」的闭环逼了出来。

### 1.5.2 又堵了一个作弊路径

`golden` 组存在一个隐蔽的作弊方式：**把 `expected.json` 写成实现当前的（错误）输出**，
这样测试会「自洽地通过」。因此新增断言：

> `expected.json 必须等于参考实现的真值`（`HARD_GOLDEN` 常量交叉校验）

L4 里的 `hard-cheat-golden` 变异体专门验证这条断言——它同时植入 JS 余数缺陷 + 自洽的
`expected.json`，**golden 测试会通过，只有这条防作弊断言能拦住**。

## 2. L3 · 对照实验（ablation）

固定任务集与模型，**只改变 Agent 的一个能力维度**，比较通过率与资源消耗。

| 组 | 配置 | 验证什么 |
|---|---|---|
| A · 完整配置 | 15 工具 + 规划 + 压缩 | 基线 |
| B · 无任务规划 | `plan: false` | 「先规划」的增量 |
| C · 无自我验证 | 移除 `run_tests` | 「改完自己跑测试确认」的增量 |
| D · 无文本检索（grep） | 移除 `grep` | 文本检索的增量（保留 AST / 语义检索） |
| E · 无 AST/语义检索 | 移除 `search_ast` + `search_semantic` | 结构化/向量检索相对 grep 的增量 |
| F · 无任何检索 | 移除三种检索 | 「能检索」的总增量 |
| G · 无上下文压缩 | `useCompression: false` | 压缩对长链路的影响 |
| H · 裸模型 | 无工具、单次输出全部文件 | **Agent 范式相对 single-shot 的增量** |

实现方式：`runAgent` 增加 `plan` / `toolFilter` / `useCompression` 三个开关；
工具子集由 `TOOLS` **派生**（`without(...)`），新增工具后无需手工同步；
裸模型组由 `ablation.ts` 独立执行（一次性喂入全部文件、解析 `<file path="...">` 标签写回）。

**记录指标**：通过率、平均步数、平均工具调用次数、平均耗时、平均 token。

### 2.1 弱模型对照

A/B/C/D/E 用的是强模型（`qwen3.8-max`）。强模型下 single-shot 已经能解决小任务，
看不出 Agent 迭代的价值。因此额外用**弱模型**（`qwen3.5-flash`）跑一遍 full vs no-verify，
观察「模型能力不足时，Agent 的迭代与自验证是否补得回来」。

## 3. L4 · 评测灵敏度检查（mutation testing）

### 3.1 做法

拿一份**已知正确的参考解**（`assets/reference-solution/` 与 `assets/hard-reference/`），
故意破坏成若干退化/作弊版本，再跑一遍评测断言：

- **检出** = 至少有一条断言失败 → 评测对该类缺陷敏感
- **漏检** = 全部断言仍通过 → **评测存在盲区，必须修断言，而不是改结论**

11 个变异体（7 个针对常规项目，4 个针对难任务项目）：

| 变异体 | 类别 | 模板 | 模拟什么 |
|---|---|---|---|
| 删空测试文件（只留恒过用例） | 作弊 | default | Agent 修不动时最省事的作弊 |
| 保留测试名但删掉全部 assert | 作弊 | default | 更隐蔽的作弊 |
| `average` 分母 off-by-one | 退化 | default | 经典边界缺陷 |
| `maxOf` 未导出 | 退化 | default | 实现对但忘了 export |
| `fibonacci` 改回朴素递归 | 退化 | default | 功能对但性能退化 |
| `clamp` 只夹下界、漏掉上界 | 退化 | default | 常见遗漏 |
| `clamp` 上下界返回反了 | 退化 | default | 复制粘贴错误 |
| **[难] 所有运算符同级** | 退化 | hard | 优先级缺陷（`2+3*4` → 20） |
| **[难] 去掉一元负号** | 退化 | hard | `-3 + 5` 抛错 |
| **[难] JS 余数代替数学取模** | 退化 | hard | `-7 % 3` → -1（期望 2） |
| **[难] 伪造 expected.json 使其自洽** | 作弊 | hard | **golden 测试会通过，只有防作弊断言能拦住** |

### 3.2 ⚠️ 等价变异体必须剔除

最初写的变异体是 `clamp` 的 `x < lo` → `x <= lo`，结果**没被检出**。
排查后发现：对 `x == lo`，两个分支返回同一个值，**在 1200+ 组输入下输出完全一致**——
这是**语义等价的变异体**，不是评测盲区。

> 教训：变异测试必须做等价性判别，否则会**误判自己的评测有洞**，
> 进而去改断言迎合一个根本不存在的问题。等价变异体应剔除出分母。

剔除后重跑：**基线全通过 + 检出率 100%（11/11）**，其中作弊类 3/3、逻辑退化类 8/8。

## 4. L5 · 失败模式分类（failure mode classification）

### 4.1 为什么需要它

通过率只回答「差多少」，不回答「差在哪」。同一个 `0/3`，可能是模型能力不足，
也可能是 Agent 流程缺失（从不自验证），还可能是评测本身有坑（作弊断言没拦住）。
把失败**归类**之后，才能对症下药。

### 4.2 信号 → 模式

从 Agent 事件流采集信号：工具调用及成败、是否写入过文件、是否调用过 `run_tests`、
测试失败次数、是否正常收尾、是否超步数、是否 API 异常；再结合断言结果分类。

分类按「信息量最大」优先：

| 优先级 | 模式 | 触发条件 | 指向 |
|---|---|---|---|
| 1 | `api_error` | 事件流报错 | 基础设施（重跑 / 限流） |
| 2 | `cheated` | 防作弊类断言失败 | Agent 绕过了真正的修复 |
| 3 | `max_steps` | 未收尾且到步数上限 | 链路太长 / 打转 |
| 4 | `no_edit` | 未写入任何文件 | 没真正动手 |
| 5 | `not_verified` | 改了但从未跑测试 | **流程缺失** |
| 6 | `tests_still_failing` | 跑过测试且失败 | 能力 / 上下文问题 |
| 7 | `tool_error` | 有工具调用失败 | 工具参数 / 环境 |
| 8 | `assertion_mismatch` | 其他断言不符 | 改错目标 / 漏要求 |

每条诊断附带**证据**（原始信号）与**改进建议**，输出到报告与 UI。

### 4.3 为什么这层很有用

它把「评测」从打分器变成了**诊断器**：跑完一轮评测，除了通过率，
还能看到「失败里有几个是 `not_verified`」——如果这个数字高，说明该改 Agent 流程而不是换模型。

## 4.5 检索能力：AST + 向量语义检索

### 4.5.1 为什么不用纯 grep

`grep`（文本检索）是纯文本匹配，有两个硬伤：

1. **噪声**：搜 `sum` 会命中注释、字符串、变量名，无法区分「定义」与「调用」；
2. **答不了结构问题**：「这个文件导出了什么」「谁调用了 `fibonacci`」——grep 给不出。

### 4.5.2 两个新工具

| 工具 | 原理 | 回答什么 |
|---|---|---|
| `search_ast` | TypeScript 编译器 API 解析源码 → 符号索引（函数/类/方法/变量/调用/导入导出） | 谁定义、谁调用、谁导出；**不受注释/字符串干扰** |
| `search_semantic` | 代码按顶层声明切块 → TF-IDF 词袋向量 → 余弦相似度 top-K | 「处理某某逻辑的那段代码」，不依赖记住函数名 |

两者都是**离线、确定性**的：不调用任何外部 embedding 服务，可重复复现。

分词器做了中文支持：ASCII 标识符按 camelCase / snake_case 拆分并去停用词，
连续中文按 **2-gram** 切分（单字太碎、长串太粗），因此中文自然语言查询也能召回。

消融实验中，D/E/F 三组分别去掉 grep、去掉 AST+语义、去掉全部检索，
用来量化「检索能力」对跨文件任务（`hard-*`）的贡献。

## 5. 实测结果汇总

> 2026-09-26，Windows 11 / bun 1.4.2，模型 `qwen3.8-max` 与 `qwen3.5-flash`

### L1 单元测试

```
53/53 通过（沙箱安全、工具执行、AST/语义检索、上下文压缩、防作弊断言、
           难任务 FAIL_TO_PASS 前置条件、失败模式分类、评测灵敏度自检）
```

### L2 任务评测集

```
常规集：    4/4 通过（100%）      平均 ~6-8 步 / ~7-8.5 次工具调用
held-out 集：4/4 通过（100%，另一个项目 stringutils，断言全部来自预置测试）
难任务集：  3/3 通过（100%，多文件项目 hard-project）
  ✓ hard-precedence  8 步 / 14 次工具调用 / 77.4s
  ✓ hard-variables  11 步 / 16 次工具调用 / 124.5s
  ✓ hard-golden     10 步 / 16 次工具调用 / 102.5s
  平均 9.7 步 / 15.3 次工具调用 / 101.5s
```

> **诚实说明**：强模型下难任务集同样 3/3，通过率仍无差异。
> 但**过程指标出现了明确差异**：难任务的平均工具调用次数是常规任务的约 **2 倍**
> （15.3 vs 7~8.5），耗时约 2 倍 —— 说明任务确实变难了，只是这个模型扛得住。
> 要拉开通过率差异，需要用弱模型跑难任务集（复现命令见 §8）。

### L3 对照实验

**强模型（qwen3.8-max）× 4 个常规任务**

| 实验组 | 通过率 | 平均步数 | 平均工具调用 | 平均耗时 | 平均 token |
|---|---|---|---|---|---|
| A · 完整配置 | 100% (4/4) | 7.8 | 8.5 | 50.4s | **11322** |
| B · 无任务规划 | 100% (4/4) | 6.0 | 6.8 | 32.4s | 6545 |

| E · 无上下文压缩 | 100% (4/4) | 7.0 | 7.8 | 43.7s | 8570 |
| F · 裸模型 | 100% (4/4) | 1.0 | 0.0 | 32.0s | **2086** |

→ **六组通过率无差异**。唯一显著差异是成本：完整配置 token 消耗是裸模型的 **5.4 倍**。
说明当前任务集区分度不足。

**弱模型（qwen3.5-flash）× 同一批任务**

| 实验组 | 通过率 | 平均步数 | 平均工具调用 | 平均 token |
|---|---|---|---|---|
| A · 完整配置 | **75% (3/4)** | 6.5 | 5.8 | 6156 |
| C · 无自我验证 | **50% (2/4)** | 7.8 | 7.0 | **11698** |
| F · 裸模型 | **50% (2/4)** | 1.0 | 0.0 | 3771 |

→ 「改完自己跑测试确认」带来 **+25pp**（50% → 75%）。且 C 组更贵（不跑测试只能反复试错）。

**重复运行方差**：完整配置 × 4 任务 × 3 轮 = **12/12 通过**，未观察到方差。

```
  作弊类：2/2      逻辑退化类：5/5

```

## 6. 结论：这些数字说明了什么

1. **「4/4 通过」的边际信息量很低** —— 强模型下，连不用工具的裸模型都能 4/4。
   通过率只证明「链路可用」，不证明「Agent 设计优越」。
2. **Agent 范式的价值出现在模型不确定的时候** —— 弱模型下，自我验证带来 +25pp。
   这比任何通过率都更能说明「为什么需要 Agent 而不是一次 prompt」。
3. **成本必须和效果一起报** —— 完整配置比裸模型贵 5.4 倍。
   在简单任务上，这个投入是浪费的。
4. **评测本身也需要被评测** —— 7 个变异体全检出、1 个等价变异体被正确剔除、
   1 个作弊盲区被修复。评测器不是「写一次就对了」的东西。

## 7. 已知局限（主动写明）

1. **常规/held-out 任务规模仍小**：单文件、单 bug 级别，强模型 single-shot 就能做对，
   区分度不足。**已通过新增难任务集（多文件 / 长链路 / 环境反馈）缓解**，
   但难任务集目前只有 3 个，样本仍然偏少，且仍是「自制小项目」而非真实仓库。
2. **没有真实仓库**：真正的 SWE-bench 用真实 GitHub issue + 真实仓库 + Docker，
   本项目只是**方法论复刻**（预置失败测试 + held-out + 对照 + 变异 + 失败分类），不能与 SWE-bench 分数类比。
3. **样本量小**：4 + 4 + 3 个任务，谈不上统计显著性；已用 3 轮重复观察方差作为补充。
4. **没有多 Agent / 多框架对照**：只对照了「无工具 single-shot」，没有对照 LangChain 等其他实现。
5. **断言仍以「测试退出码 + 文件内容」为主**：没有检查代码质量（复杂度、可读性）、
   没有检查工具副作用（如 Git 提交信息是否合理）。
6. **失败模式分类是启发式**：优先级规则由人设定，可能存在误判（例如「改了但没跑测试」
   也可能同时是「能力不足」）；它给出的是**首要归因**，不是唯一原因。

## 8. 复现命令

```bash
# L1 单元测试（67 条，含灵敏度检查与失败分类）
bun test tests/agent.test.ts

# L2 常规评测集
bun scripts/run-eval.ts --only default
# L2 held-out 评测集
bun scripts/run-eval.ts --only holdout
# L2 难任务集（多文件 / 长链路 / 环境反馈），输出含失败模式分类
bun scripts/run-hard.ts
bun scripts/run-hard.ts hard-golden          # 只跑指定难任务

# L3 对照实验（7 组 + 裸模型组）
bun scripts/run-ablation.ts --only default
bun scripts/run-ablation.ts --only hard --configs full,no-search   # 检索对跨文件任务的贡献
bun scripts/run-ablation.ts --only default --configs full --repeat 3 --no-bare  # 方差

# L4 评测灵敏度检查（不需要 LLM，11 个变异体）
bun scripts/check-sensitivity.ts

# 类型检查
bun run typecheck
```

所有报告会落盘：`ablation-*.json/txt`、`sensitivity-report.json/txt`、`hard-report.json/txt`。
